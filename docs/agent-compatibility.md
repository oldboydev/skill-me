# Compatibilidade de agentes — diagnóstico local (doctor)

Este documento separa três camadas de evidência para cada fato usado pelo
`doctor` (issue #3): **contrato documentado** (o que a fonte oficial declara),
**inspeção estática** (o que o `doctor` lê de artefatos/config locais, sem
executar o agente) e **execução real** (comportamento observado rodando o
agente de verdade). Esta entrega só produz as duas primeiras; a coluna de
execução real está vazia por desenho — `runtimeVerification` é sempre
`not_performed` (critério 6).

## Launchers e fonte de versão (critério 2-3)

Resolução no PATH: em cada diretório, na ordem do PATH, o `doctor` testa o nome do agente; no
Windows, testa `<agente><ext>` para cada extensão de `PATHEXT` do ambiente (entradas que não sejam
uma extensão simples são ignoradas; sem `PATHEXT`, `.com;.exe;.bat;.cmd`), como o Windows resolve um
comando sem extensão. O primeiro candidato existente vence, mesmo de formato não reconhecido
(`codex.exe` do app do Codex, `claude.cmd` de um npm global): ele fica `present` com `version: null`,
nunca `absent`, e a versão de uma instalação de diretório posterior não lhe é atribuída. Executável
nativo (cabeçalho PE/ELF/Mach-O) de Codex ou Hermes é examinado só pelo cabeçalho, sem leitura como
texto. A preferência do PowerShell por `.ps1` é do shell, não do SO, e não é modelada.

**Corrigido na revisão formal3** (`.checks/code-review/formal3-fixes.md`, item 1): um `package.json`
do Codex com o JSON válido `null` (ou outro primitivo/array no lugar do objeto esperado) fazia
`parsed.name` lançar `TypeError`, escapando para o `catch` de `resolveOneAgent` e virando
`presence: unknown` — mesmo com o artefato encontrado e lido com sucesso, violando o critério 3
(artefato presente com metadado ilegível nunca é confundido com presença indeterminável). Agora
`null`/primitivo/array no lugar do objeto de metadado cai na mesma resposta de "não reconhecido"
(`presence: present`, `version: null`, `launcher_not_recognized`) que um `name` divergente já usava.

## Estados e vocabulário (critérios 5-12)

- `support` na CLI local, decidido nesta ordem: launcher ausente no PATH
  consultado → `unavailable/executable_not_found` (a única ausência que a
  leitura comprova; IDE, desktop e cloud continuam
  `unverified/surface_not_inspected`); presença `unknown` →
  `presence_undetermined`; versão nula → `version_unresolved`; versão fora
  de um perfil examinado nesta entrega (Claude 2.1.295, Codex 0.162.1,
  Hermes 0.21.4) → `version_profile_incompatible`; depois, a tabela de
  contrato da própria instalação (hoje só o `VALID_HOOKS` do Hermes) decide
  `verified/local_contract_lists_events` ou um `unverified` com motivo
  próprio (`contract_event_not_listed`, `contract_source_not_found`,
  `contract_source_unreadable`, `input_too_large`,
  `contract_changed_during_read`, `contract_source_unrecognized`,
  `no_static_contract_source`). Documentação isolada, uma versão mais nova
  ou uma tabela escrita pelo próprio `doctor`/config do usuário nunca
  bastam.
- `evidence.origin`: `real_environment` para o que a CLI leu do ambiente que
  recebeu (inclusive quando um teste montou esse ambiente — o registro do
  cenário de teste é que declara `fixture`), `not_inspected` para toda
  superfície não inspecionada e como padrão quando nenhuma origem é
  informada, `fixture` só quando uma prova a passa explicitamente, e
  `documented_contract` só na `exclusion` documentada.
- `configuration`/`trust`: estados observados de leitura, nunca autorização
  concedida pelo `doctor`. Um campo arbitrário dentro do próprio arquivo de
  hooks (ex.: alguém escrever `"trust": "trusted"` no mesmo JSON/YAML) nunca
  é aceito como consentimento nativo — só a origem `hooks_auto_accept` do
  Hermes, lida por um leitor dedicado e validado contra uma lista reconhecida,
  pode produzir `trusted`.
- `runtimeVerification`: sempre `not_performed` nesta entrega — contrato
  documentado e inspeção estática nunca substituem execução real.
